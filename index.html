Parback

Voice-assisted inventory counting for restaurants and bars, designed for less friction.

01

Problem

Inventory counting is a recurring, hands-on job. Someone walks through the storage areas, identifies each product, and records a quantity.

Observed firsthand

Counts are typically done by hand on a clipboard. In my experience, one person can count a small inventory, while a large one is often counted by two to keep it moving. Entering each count by hand is repetitive.

Ordering is also a separate step from counting. Distributors set a minimum per delivery, and the person doing the count often doesn't know those minimums. That knowledge usually sits with the manager, so the count and the order decision end up disconnected.

Colleague feedback

Colleagues have shared inventory pain points with me informally. One mentioned order minimums during service, which prompted me to build minimum tracking into the app. This was informal feedback, not formal research.

To validate

Whether this friction is common across venues, how long counting actually takes, and whether Parback reduces it.

02

Workflow

Inventory isn't only data entry. A bartender moves through physical storage areas while identifying products and recording quantities, so the product needed to follow that movement instead of just offering a form.

  1. 1Move through a location
  2. 2Identify the bottle or product
  3. 3Record the count
  4. 4Progress to the next location
  5. 5Export the completed count
Hypothesis, not yet tested

If manual entry is reduced and the interface follows the physical counting workflow, one person may be able to complete a count with less friction.

03

Product decisions

Each feature traces back to a specific need. The benefits are intended, not measured.

Need Decision Intended benefit (not measured)
Entering each count by hand is repetitive Voice-assisted input Less manual entry during the count
People may prefer different ways to start voice input Design choice, untested Hold-to-speak or tap-to-speak, switchable in settings Lets the counter use whichever input style fits how they work
Spoken counts need to become structured data AI parsing into structured entries Spoken counts become usable records without retyping
Inventory is spread across physical storage areas Selectable count locations (Well, Back Bar, Fridge, Liquor Room) Counts include the areas a venue actually uses
A counter needs orientation while moving through a space Location-based progress bar Built; not yet triggered in testing Intended to show where you are in the count (not yet observed)
Fast voice entry makes accidental duplicates easy Swipe-to-delete on entries A mistaken entry can be removed without restarting the count
Counts have to end up somewhere usable CSV export for Excel or Google Sheets Finished counts open in tools a venue may already use
The count and the order decision are disconnected Distributor minimums stored in the app's settings First step; no calculation yet Puts the order constraint inside the app, as groundwork for connecting counts to ordering (not yet built)

06

What broke

Four things surfaced in my own testing.

  1. Voice input failed silently on Safari

    Voice parsing worked in Chrome but failed in Safari on iPhone without showing any error. I'm designing for a phone, and a desktop-only test would have missed it. A failure with no visible error is worse than one you can see.

  2. Fast voice entry made double-counts easy

    Counting at home, I added the same bottle twice by calling it out again after I'd already counted it. An early bug had also merged duplicate entries.

  3. Spoken brand names were misparsed

    The parser was working from the raw transcript or letting the AI guess brand names.

  4. The progress bar never triggered

    The location progress bar never triggered in home testing. Par levels default to zero, and there's no editable par field yet.

07

What changed

Each change below matches the problem with the same number in What broke.

  1. Fixed

    Traced the Safari failure and fixed it

    It was a Safari-specific request issue. To validate I tested on iPhone because I expect that's what venue staff carry. I haven't confirmed that.

  2. Changed

    One row per entry, plus swipe-to-delete

    After the merge bug, I changed the app to add a new row for each entry so every bottle stays visible. That left no way to remove a mistaken row, so I added swipe-to-delete as error recovery. For a voice-first tool, fast input only works if mistakes are cheap to fix.

  3. Changed

    Matched speech against the existing inventory

    The parser now matches against the existing inventory list instead of relying on the raw transcript or letting the AI guess.

  4. Not fixed

    Progress bar is still open

    Without editable par levels, the progress feature is built but unvalidated.

08

What I'd validate next

Planned, not completed

  • Observe bartenders and managers doing real inventory counts, and establish baseline count time and common errors.
  • Have people other than me test Parback, across different venue layouts and devices.
  • Measure whether voice input reduces friction or introduces new correction and error patterns.
  • Test whether the location and progress model generalizes beyond the workflows I already know.
  • Learn how managers actually move from a completed count to an order before building recommendations around stored distributor minimums.
09

What I learned

  • Firsthand domain knowledge is useful, but it doesn't replace user validation.
  • Understand the real workflow before designing the interface.
  • Turn pain points into specific requirements.
  • Shipping something testable exposes assumptions.
  • Product decisions should follow evidence, not attachment to the original idea.
  • Building features before testing is easy. Knowing which ones matter takes validation.
